1権限体系の概要（3層モデル）

IFS Cloud の権限制御は 認証 (Authentication) → 認可 (Authorization) → データアクセス制御 (Data Access Control) の3層で構成されます。認可はサーバー側ビジネスロジックで完結しており、クライアントを改ざんしても回避できません。

認証 Authentication
IAM
IFS IAM (Identity and Access Manager) / SSO / MFA で本人確認。ログイン後は JWT トークンを発行
認可 Authorization
Permission Set
サーバー側で Projection・Action・System Privilege を検証。クライアント非依存
データアクセス制御
ACL / View
DB Viewによるフィルタリング / ACL (Access Control Lists) で行レベルのデータ制御
ℹ️
役割ベースアクセス制御 (RBAC)

IFS Cloud は RBAC (Role-Based Access Control) を採用しています。ユーザーに直接権限を付与するのではなく、Permission Set（ロール）を介して権限を管理します。ユーザーが職務変更した場合は Permission Set の付け替えで対応できます。Permission Set 同士を Grant し合う構造（Grant Structure）により、複雑な業務ロールを柔軟に構築できます。

認可の適用範囲

認可対象説明
機能認可 (Functional Authorization) ユーザーが実行できる操作・プロシージャを制御。Projection の Access Level・Action 単位で管理
データ認可 (Data Authorization) ユーザーが操作できるデータの範囲を制御。DB View フィルタリングおよび ACL で実装。モジュールごとに実装が異なる

参考: IFS TechDocs — User Authorization (25R2)

2Permission Set の種別と Delivery Type

Permission Set は Projection・Lobby・Workflow・Database Task・System Privilege へのアクセス権をまとめたコレクションです。ユーザーまたはユーザーグループに直接割り当てます。

End-User Role

ユーザーに直接 Grant できるロール。複数の Functional Role を束ねた「最終的な業務ロール」として設計します。

  • User / User Group への直接 Grant 可能
  • Functional Role を内包（Grant Structure）
  • 複数の業務フローをカバー
  • 例: 「購買担当者」「在庫管理者」「経理担当」

Functional Role

特定の小さな業務フローをカバーするロール。再利用を前提に設計します。

  • User への直接 Grant は不可
  • End-User Role の Grant Structure に組み込む
  • できる限り小さく・再利用可能に設計
  • 例: 「発注入力」「発注承認」「在庫移動」

Delivery Type（配布種別）

Delivery Type作成者変更可否用途
IFS_MANAGE_BASE IFS Frameworks 変更不可（ユーザー追加/削除のみ） 特殊な認可要件。LTU Permission Set 構造に含めることが許可。
例: FND_WEBENDUSER_MAIN、FND_ADMIN
IFS_MANAGE IFS（標準製品） 変更不可（ユーザー追加/削除のみ） 特定の業務フローをカバーする IFS 標準 Permission Set
CUSTOM 顧客 / パートナー 変更可（全ライフサイクルを Solution Manager で管理） IFS Cloud 管理画面から作成した全 Permission Set。カスタマイズ・維持管理の主体

参考: IFS TechDocs — Permission Set Overview (25R2)

⚠️
IFS_MANAGE_BASE / IFS_MANAGE は変更禁止

IFS が提供する標準 Permission Set はユーザー/ユーザーグループの追加・削除以外の変更ができません。Projection の Grant 変更・System Privilege の変更は行えません。標準ロールをベースにカスタマイズしたい場合は、CUSTOM Permission Set を作成して Grant Structure で組み合わせてください。

3階層構造図（User → Permission Set → Grant Object）

権限の付与は「ユーザー → End-User Role → Functional Role → Grant 対象（Projection・Lobby・Workflow 等）」という階層で管理されます。

図3-1: IFS Cloud 権限体系の全体像 — User から Grant Object（Projection・System Privilege 等）までの階層
💡
階層設計の推奨パターン

User → End-User Role（例: 購買担当者）→ Grant Structure に複数の Functional Role（発注入力・発注承認・サプライヤー照会）を含める。さらに FND_WEBENDUSER_MAIN を Grant Structure に必ず含め、IFS Cloud Web の基盤機能が常に利用可能な状態にします。

4Projection と Access Level

Projection は IFS Cloud の中心的な API 単位であり、認可の主要ポイントです。1つの Projection はデータビュー（Entity・Query 等）と Operations（Function・Action）を一体として実装します。IFS Cloud Web クライアントはすべて Projection 経由でサーバーと通信します。

ℹ️
Projection は旧来の「Function Area」に相当

IFS Applications の旧バージョンで使用されていた「Function Area」は、IFS Cloud では Projection に統合されました。Projection は自己完結型の Web API として実装されており、業務機能の単位で認可を管理します。1つの Projection に対して複数のクライアントページが紐づく場合があります。

図4-1: Projection の Access Level — Full / Read Only / Custom / None の権限範囲

アクションの2種類（重要）

Projection 内のアクションは以下の2種類に分類されます。この区別が Access Level の正確な意味を理解する上で重要です。

アクション種別説明典型例
Entity Action
エンティティアクション		 Projection 内の特定データソース（Entity）のコンテキストで呼び出されるアクション。基本的なデータ操作は crud_action という単一アクションとして実装される 各 Entity に1つの crud_action。Create / Update / Delete は一体であり個別に分離できない
Projection Action
プロジェクションアクション		 Projection 全体のコンテキストで呼び出されるアクション。特定のデータソースに縛られないカスタムビジネスロジック ApproveOrder（注文承認）、Release（リリース処理）、CalculateCost（コスト計算）等
⚠️
crud_action は単一エンティティアクション——Create / Update / Delete を個別制御できない

crud_action は Entity ごとに1つ存在する不可分なアクションです。「更新は許可するが削除は禁止」という制御を Entity Action の Grant/Revoke で実現することはできません。この粒度の制御が必要な場合は、Projection Action（カスタムビジネスロジック）側で実装する設計が必要です。

Access Level 詳細

Access LevelEntity Actions
(CRUD系)		Projection Actions
(カスタムロジック)		説明
Full ✅ 全て Grant ✅ 全て Grant 利用可能なすべての Entity Actions と Projection Actions が Grant される。ただし Projection の設計上 Create/Delete が禁止の場合は例外
Read Only ✗ 全て未付与 ✗ 全て未付与 データ参照（Query）のみ。Entity Actions も Projection Actions もいずれも Grant されない。一部の Projection は設計上 Read Only のみ（by design）
Custom △ crud_action 単位で設定
（C/U/D の個別制御不可）		 △ Action 単位で個別設定可 Entity Action（crud_action単位）または Projection Action を個別に Grant / Revoke した状態。Full から一部 Revoke、または Read Only から一部 Grant した場合に自動的に Custom になる
None ✗ ✗ Projection が Permission Set に Grant されていない状態。紐づくクライアント画面へのアクセスも不可
⚠️
権限 Revoke 後はセキュリティキャッシュのリフレッシュが必要

Entity Action または Projection Action の Grant/Revoke を行った後は、Refresh Server Cache ページからセキュリティキャッシュを更新しないと変更が反映されません。

参考: IFS TechDocs — Projection (25R2) / Manage Projection Grants (25R2)

Projection とクライアントページの関係

  • 1 Projection に複数のクライアントページが紐づく場合がある
  • Projection を Grant するとその Projection を使用するすべてのページがアクセス可能になる
  • ナビゲーターに表示されるページには「In Navigator」バッジが付く
  • コマンド・リンク経由でのみアクセス可能なページも存在する

Projection Grant の管理方法

  • Direct Grants: Projection を直接指定して Grant
  • Manage by Page: ページから使用 Projection を逆引きして Grant
  • Manage by Navigator: ナビゲーター構造から一括 Grant（標準推奨）
  • Access Level 変更: Full → Custom → Read Only の順で制限強化

ナビゲータ定義と権限設計のセット実施（標準プラクティス）

IFS Cloud では ナビゲータ定義（メニュー構造） と Permission Set の Projection Grant を同時に設計するのが標準的な実施方法です。「どのロールにどのメニューを見せるか」と「どのロールにどの Projection を Grant するか」は表裏一体だからです。

① ロール別ナビゲータ定義（メニュー定義）

  • ロール（業務担当者）ごとに表示するメニュー項目を決定
  • Manage by Navigator でナビゲーター上のページを選択 → 対応する Projection が自動特定される
  • 「In Navigator」バッジのあるページが主対象。コマンド・リンク経由ページは別途確認

② メニュー定義 × 権限マトリクス

  • ロール（縦軸）× 機能/ページ（横軸）のマトリクスを作成
  • 各セルに Access Level（Full / Read Only / Custom / None）を記載
  • このマトリクスが Permission Set 設計の正文書（Single Source of Truth）となる
  • 定期レビュー時もマトリクスを起点に過剰権限を検出
💡
推奨手順

① ロールと業務フローを定義 → ② ロール別に表示メニュー（ナビゲータ）を決定 → ③ Manage by Navigator で Projection を特定・Grant → ④ メニュー定義 × 権限マトリクスに転記して管理文書化 → ⑤ 承認後 Permission Set に反映

5Grant 対象オブジェクト一覧

Permission Set には Projection 以外にも複数のオブジェクトを Grant できます。

Grant 対象説明管理方法
Projection IFS Cloud Web の主要 API 単位。データ取得・操作の認可ポイント Solution Manager の Permission Set 画面 → Projections タブ
Reports Operational Reports / Quick Reports へのアクセス。Projection Grant 経由で制御（個別の Grant オブジェクトではなく Projection に紐づく） 対応する Projection を Grant することでアクセス可能
Lobby（ダッシュボード） Lobby Data Source・Element・Page の3レベルで制御可能 Permission Set 画面 → Lobbies タブ
Workflow（ワークフロー） 承認フロー等のワークフロー利用権限。Workflow 自体の Grant と、使用する Projection の Grant を両方付与する必要がある Permission Set 画面 → Workflows タブ + Projections タブ
Database Tasks / Task Chains バックグラウンドジョブの実行権限。スケジュールされたタスクやタスクチェーンを実行するには本 Grant が必要 Permission Set 画面 → Database Tasks タブ
System Privileges CONNECT・ADMINISTRATOR 等の特権。データ・メソッド認可とは独立した高権限機能 Permission Set 画面 → System Privileges タブ
⚠️
Workflow は Projection Grant も必要

Workflow を利用可能にするには、Workflow 自体の Grant に加えて、そのワークフローが使用する Projection の Grant も別途付与する必要があります。Workflow だけ Grant しても、Projection が未 Grant の場合は機能しません。

6System Privileges リファレンス

System Privilege はデータ・メソッド認可とは独立した「システム全体の特権」です。作成・変更はできません。Permission Set を介してのみユーザーに付与されます。

🔒
System Privilege は最小権限の原則で厳格に管理

特に ADMINISTRATOR・DEFINE SQL・IMPERSONATE USER は非常に高い権限です。通常業務ユーザーには絶対に付与しないでください。付与が必要な場合は理由を記録し、定期的に棚卸しを実施してください。

System Privilege用途リスクレベル
CONNECT IFS Cloud クライアントからアクセスするすべてのユーザーに必須。未付与の場合 HTTP 401 Unauthorized が返される。IFS ミドルウェアサービスへのアクセスを許可 必須 / 標準
ADMINISTRATOR Appowner 相当の権限（メソッドセキュリティは除く）。通常より多くのデータを参照可能。FND_ADMIN Permission Set に付与済み。Batch Queue の削除・全スケジュールタスク操作・全ユーザーへのプロパティ設定等が可能 ⚠️ 最高権限
IMPERSONATE USER 認証ユーザーが別のユーザーとして操作（なりすまし）を実行できる。サポート・デバッグ目的 ⚠️ 最高権限
DEFINE SQL アプリケーション経由で任意の SQL を実行できる。スケジュールタスク定義・データアーカイブ・クイックレポート定義・設定アイテム定義が可能。DBビュー経由で任意のデータにアクセス可能 ⚠️ 高権限
DEBUGGER IFS Cloud デバッグコンソールでサーバーのスタックトレースを取得できる 開発者向け
LOBBY DATASOURCE DESIGNER Lobby データソースの設定を変更できる。注意: 全 View/Table をクエリ可能 設計者向け
DOCMAN ADMINISTRATOR Document Management コンポーネントの管理者権限 コンポーネント管理
EXPCTR ADMINISTRATOR Export Control コンポーネントの管理者権限 コンポーネント管理

参考: IFS TechDocs — System Privileges (25R2)

7Grant Structure（Permission Set の階層化）

Grant Structure は複数の Permission Set を階層化する仕組みです。Permission Set A が Permission Set B・C を Grant した場合、A のユーザーは B・C の全権限も持つことになります。

Grant Structure の仕組み

  • ある Permission Set（A）に別の Permission Set（B）を Grant できる
  • A のユーザーは B の全 Projection Grant・System Privilege も継承
  • 循環 Grant（A→B→A）は不可
  • 合計権限 = 直接 Grant + 間接 Grant（ツリー全体）の合計
📐

サイズ上限: 2MB
Grant Structure が大きくなるとパフォーマンスに影響。小さくモジュール化した Permission Set を推奨

推奨 Grant Structure パターン

End-User Role「購買担当者」
  ├─ Functional Role「発注入力」
  │    └─ Projection: PurchaseOrderEntry (Full)
  ├─ Functional Role「発注承認」
  │    └─ Projection: PurchaseOrderApproval (Full)
  ├─ Functional Role「サプライヤー照会」
  │    └─ Projection: SupplierQuery (Read Only)
  └─ FND_WEBENDUSER_MAIN  ← 必須（基盤機能）
       └─ System Privilege: CONNECT
✅
FND_WEBENDUSER_MAIN を必ず Grant Structure に含める

IFS Cloud Web の必須フレームワーク機能（ナビゲーション・設定・通知等）は FND_WEBENDUSER_MAIN に含まれています。すべての End-User Role の Grant Structure にこの Permission Set を含めることを推奨します。

参考: IFS TechDocs — Grant Structure (25R2)

8Security Checkpoints（再認証・監査証跡）

Security Checkpoint は特定の業務フロー・機能において、権限を持つユーザーであっても再度パスワード認証を要求する仕組みです。不正操作の防止と監査証跡の確保を目的とします。

主な用途

  • 高額発注の最終承認
  • 支払情報（銀行口座等）の変更
  • 重要マスタデータの削除
  • 不正経理リスクのある処理（仮請求書の承認等）
⚠️

放置された PC からの不正操作を防ぐ最後の防衛線。「何かおかしい」と感じた場合は Cancel ボタンで処理を中断・確認できる設計

Security Checkpoint Gate

  • 設定部分: 一意 ID・説明・監査ログメッセージ（代替パラメータ付き）
  • 実装コード: 業務フローのどこかで Gate が呼び出される
  • 同一トランザクション内で複数の Gate が有効な場合、最初の Gate 通過後は他の Gate はオープン状態（再認証不要）
  • Gate を有効/無効に切り替えることができる

Security Checkpoint のコンポーネント

コンポーネント説明
Username デフォルトでログイン中ユーザーの名前が自動入力。設定によっては再入力を強制可能。他ユーザーの名前では通過不可
Password デフォルトの認証方式。ユーザーが正しいパスワードを入力して再認証
Comment トランザクションに対するコメントを任意入力。監査担当者の調査効率向上（不審に見えない正当な取引への説明を記録）
Security Checkpoint Log 誰が・いつ・何を通過したかの監査ログ。SECURITY_CHECKPOINT_SUCCESS イベントでメール等を送信可能

参考: IFS TechDocs — Security Checkpoints (25R2)

9標準 Permission Set リファレンス

IFS が提供する主要な標準 Permission Set の一覧です。これらは IFS_MANAGE_BASE または IFS_MANAGE Delivery Type で変更不可です。

Permission Set 名Delivery Type用途注意点
FND_WEBENDUSER_MAIN IFS_MANAGE_BASE IFS Cloud Web の基盤機能（ナビゲーション・設定・通知等）へのアクセス。全 End-User に必要 すべての End-User Role の Grant Structure に含めること
FND_WEBENDUSER_B2B IFS_MANAGE_BASE B2B ポータルユーザー向けの基盤機能。外部パートナー・サプライヤー向け B2B ユーザーの Grant Structure に使用
FND_ADMIN IFS_MANAGE_BASE System Privilege: ADMINISTRATOR が付与されたシステム管理者用 Permission Set 最高権限。システム管理者専用。通常業務ユーザーへの付与禁止
FND_WEBENDUSER_SOL IFS_MANAGE_BASE Solution Manager アクセス用の基盤 Permission Set Solution Manager を使用する管理者向け
ℹ️
Deprecated / Obsolete Permission Set

IFS は製品バージョンアップとともに旧来の Permission Set を廃止することがあります。TechDocs の「Deprecated and Obsolete Permission Sets」ページで最新状況を確認し、廃止対象の Permission Set を使用している場合は移行計画を立ててください。

10権限設計のベストプラクティス

Permission Set 設計

  • Functional Role は 小さく・再利用可能 に設計
  • End-User Role は業務ロール単位で作成（「購買担当者」「倉庫担当」等）
  • 必ず FND_WEBENDUSER_MAIN を Grant Structure に含める
  • Grant Structure は 2MB 以内に収める
  • CUSTOM Permission Set のみ変更・管理対象とする

System Privilege 管理

  • ADMINISTRATOR を通常業務ユーザーに付与しない
  • DEFINE SQL を一般ユーザーに付与しない
  • IMPERSONATE USER は特定のサポート担当者のみ
  • LOBBY DATASOURCE DESIGNER は設計担当者限定
  • 全ユーザーに CONNECT を付与する（必須）
  • System Privilege は定期的に棚卸しを実施

Access Level の選択基準

ケース推奨 Access Level
データ照会のみ（参照ユーザー）Read Only
標準業務操作（入力・更新）Full
削除を除く業務操作Custom (Delete Revoke)
未付与（アクセス不要）None（Grant しない）

Security Checkpoint 適用基準

  • 高額・高リスクな承認操作（発注承認・支払承認等）
  • マスタデータの削除・変更（銀行口座・単価等）
  • SOX / 内部統制上のキーコントロールとなる操作
  • 監査証跡の確保が法的・コンプライアンス上必要な操作
💡
権限設計サマリー

最小権限の原則を徹底し、必要な業務に必要な Access Level のみ付与します。
CUSTOM Permission Set（Functional Role × End-User Role 階層）+ Grant Structure で業務ロールを組み合わせ、 Security Checkpoint で高リスク操作に再認証を追加することで、 IFS Cloud の権限管理は柔軟かつセキュアに実現できます。

11AI / 非人間アイデンティティ（NHI）向け権限設計

IFS Cloud の REST API / OData Projection は AI エージェントや自動化ツールから直接呼び出せます。これらの非人間クライアントに対しても、人間ユーザーと同様に Permission Set による認可制御が適用されます。しかし、AI 特有のリスク（プロンプトインジェクション・過剰エージェンシー）があるため、より厳格な設計が必要です。

🤖
OWASP LLM06:2025 — Excessive Agency（過剰エージェンシー）

AI エージェントに必要以上の権限を与えると、プロンプトインジェクション・幻覚（Hallucination）・誤ったツール選択によって、意図しない更新・削除・機密データ取得が発生します。これは IFS Cloud への書き込み Permission Grant が過剰な場合に現実のリスクとなります。根本原因は「過剰機能・過剰権限・過剰自律」の3つです。

非人間アイデンティティ（NHI）の概念

AI エージェント・RPA・外部連携システム等の自動化クライアントは Non-Human Identity（非人間アイデンティティ） として管理します。人間ユーザーとはライフサイクルが異なるため、別途管理戦略が必要です。

1用途 = 1アカウント

IFS Cloud での AI 向け Permission Set 設計原則

設計原則IFS Cloud での実装方法根拠
1. 専用 Permission Set AI 統合ごとに独立した CUSTOM Permission Set を作成。他 AI・人間との共有禁止 侵害時の影響範囲を最小化。監査ログでの追跡を容易にする
2. 最小 Projection Grant AI が実際に呼び出す Projection のみ Grant。業務上不要な Projection は Grant しない OWASP LLM06「過剰機能」対策。攻撃面の最小化
3. Read Only を基本とする データ参照のみの AI（ダッシュボード・レポート生成等）は Read Only を徹底。
Entity Actions（Create/Update/Delete）は原則 Revoke		 OWASP LLM06「過剰権限」対策。読み取りのみなら書き込み不可
4. 書き込みは必要最小 Action のみ 書き込みが必要な場合は Full ではなく Custom Access Level を使用し、必要な Entity Action のみ Grant 例: 注文ステータス更新のみ → Update Action のみ Grant し Create/Delete は Revoke
5. System Privilege は CONNECT のみ ADMINISTRATOR / DEFINE SQL / IMPERSONATE USER は絶対付与しない。CONNECT のみ System Privilege の侵害は全データへのアクセスにつながる最高リスク
6. Human-in-the-Loop AI が高リスク操作（発注・支払等）を実行する場合は Security Checkpoint で人間承認を要求。AI の完全自律実行を防ぐ OWASP LLM06「過剰自律」対策。プロンプトインジェクション攻撃の最終防衛線

禁止事項（AI アカウント）

  • ADMINISTRATOR / DEFINE SQL の付与
  • IMPERSONATE USER の付与
  • 複数 AI ユースケースでの Permission Set 共有
  • 長期固定パスワードの使用（OAuth2 未使用）
  • Full Access Level の安易な使用（Read Only / Custom で代替）
  • FND_ADMIN Permission Set の付与
  • 廃止済み AI 統合のアカウント放置

推奨事項（AI アカウント）

  • OAuth2 Client Credentials フローで認証
  • AI 統合 1 件 = IFS アカウント 1 件 = Permission Set 1 件
  • Projection は実際に使用するもののみ Grant
  • 書き込み Permission Grant は書面で承認・記録
  • API アクティビティを監査ログで記録・モニタリング
  • 高リスク書き込みには Security Checkpoint を適用
  • 定期的に Permission Set を棚卸し、不要権限を削除

Complete Mediation（完全仲介）原則

AI エージェントが「この操作は安全だ」と判断しても、IFS Cloud の Permission Set による認可は必ずサーバー側で検証されます。AI に認可判断を委ねてはなりません。IFS Cloud の Projection ベース認可はリクエストごとに評価される設計であり、Zero Trust アーキテクチャの「Never Trust, Always Verify」原則に適合しています。
