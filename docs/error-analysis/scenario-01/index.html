STEP 3 — PL/SQL ソース解析（PURCHASE_ORDER_APPROVAL_API）

AIが PURCHASE_ORDER_APPROVAL_API のソースコードを取得し、エラー発生箇所の判定ロジックを特定しました。

-- PURCHASE_ORDER_APPROVAL_API (PURCH モジュール / Core レイヤー) -- 承認グループに対する承認者チェックロジック ELSIF (authorize_group_id_ IS NOT NULL) THEN group_description_ := Purch_Authorize_Group_API.Get_Description(company_, authorize_group_id_); IF (Purch_Authorize_Group_Line_API.Check_Authorizer_Exist( company_, authorize_group_id_, current_authorizer_id_)) = 0 THEN IF (Pur_Auth_Substitute_API.Substitute_In_Auth_Group( company_, authorize_group_id_, current_authorizer_id_) = 'FALSE') THEN IF (Purchase_Authorizer_API.Superior_Auth_In_Group( company_, authorize_group_id_, current_authorizer_id_) = 'FALSE') THEN Error_SYS.Record_General(lu_name_, 'WRONGAUTHORSUB: Authorizer :P1 does not belong to Authorization Group :P2 ...', current_user_id_, group_description_); -- ← ここでエラー発生 END IF; END IF; END IF;
STEP 4 — 根本原因の特定（AI 分析結果）

AI 分析結果 — WRONGAUTHORSUB / 承認グループ未登録

エラーコード
PurchaseOrderApproval.WRONGAUTHORSUB
発生API
PURCHASE_ORDER_APPROVAL_API（PURCHモジュール / Coreレイヤー）
判定ロジック
3段階チェック: ①グループメンバーでない → ②代替者でもない → ③上位承認者でもない → エラー
根本原因
ユーザーが承認グループに未登録。かつ代替者・上位承認者にも設定されていない。人事異動後の設定更新漏れが最有力。
影響範囲
同グループが必要な購買発注すべてで承認フローが停止
  • 即時対応: IFS Cloud → 購買設定 → 承認グループ → 対象グループにユーザーを追加
  • または: 代替者設定（Pur_Auth_Substitute_API）または上位承認者設定（Purchase_Authorizer_API）で対応
  • 確認: Purch_Authorize_Group_Line_API.Check_Authorizer_Exist が 1 を返すことを確認
  • 再発防止: 人事異動時の承認グループ更新をシステム管理チェックリストに追加
補足: 実機データ確認画面
